# Bundesliga Coach Impact Analyzer

Does a coaching change actually change results? And does the incoming coach
bring a different formation with them? This pipeline builds a match-level
Bundesliga dataset (results, formations, xG, PPDA) with the coach in charge
of each match attached, then:

1. **Coach impact rankings** — for every coaching change, compares
   points-per-game / goal difference / xG difference / PPDA in the matches
   immediately before vs. after, and ranks changes by biggest swing.
2. **Formation matchup matrix** — average points won per game for every
   (team formation, opponent formation) pairing, as a heatmap.
3. **Coach preferred formations** — each coach's most-used formation during
   their tenure, joined onto the impact rankings so you can see whether a
   PPG swing came with a tactical change too.
4. **Formation-aware outcome predictor** — Random Forest and XGBoost
   classifiers predicting win/draw/loss from formations plus rolling form,
   xG, PPDA, deep completions, and coach tenure, evaluated on a strict
   time-based holdout (see [below](#formation-aware-outcome-predictor)).
5. **`predict.py`** — a CLI that actually uses the trained models: give it
   two team names and it computes each team's current form itself and
   prints a win/draw/loss prediction (see [below](#predicting-a-match)).
6. **Coach bounce predictor** — an honest, small-sample attempt at
   predicting the SIZE of a coaching change's PPG swing from the incoming
   coach's own historical track record (see
   [below](#coach-bounce-predictor)).

![Formation matchup heatmap — average points won per game for every (team formation, opponent formation) pairing across 8 Bundesliga seasons](docs/formation_matchup_heatmap.png)

*Average points won per game by formation matchup, 2019-20 through the
ongoing 2026-27 season — generated by `src/formation_matrix.py`.*

## Data sources

| Data | Source | How |
|---|---|---|
| Results + formations | [FBref](https://fbref.com) | [`soccerdata.FBref`](https://soccerdata.readthedocs.io/en/latest/datasources/FBref.html) |
| xG + PPDA (pressing) + deep completions | [Understat](https://understat.com) | [`soccerdata.Understat`](https://soccerdata.readthedocs.io/en/latest/datasources/Understat.html) |
| Coach tenure dates | Transfermarkt "Trainerhistorie" pages | `src/fetch_coach_history.py` (custom scraper) + manual CSV fallback |

`soccerdata` doesn't cover Transfermarkt or any manager-history source, so
coach tenure is the one piece scraped by hand here. Wikipedia was tried
first — the plan was to use its "List of `<club>` managers" pages, which
looked clean and scraper-friendly — but verified live, Bundesliga clubs
mostly don't have that page on English Wikipedia (every guessed URL 404'd).
Transfermarkt's own manager-history table turned out to be the reliable
source: it returns a normal 200 to a plain `requests` call with a browser
User-Agent (no login/JS wall for this page), and the URL only cares about
the club's numeric id, verified live for Bayern Munich and Heidenheim.
Treat `data/coach_history_manual.csv` as the correction file: it
overrides/augments whatever the scraper produces, and is where you fill in
any club a live search can't confidently resolve either (see "Auto-
resolution" under [Known rough edges](#known-rough-edges-this-is-a-scaffold-not-a-finished-pipeline))
or to patch a spell it got wrong.

**Update, found live a few days after the above was working fine**:
`transfermarkt.com` started returning an AWS WAF "challenge" response (HTTP
202, empty body) to every request — including the plain homepage, so not
something a better User-Agent or a delay fixes. `transfermarkt.de` was
verified live to still serve the identical page with no challenge, so
`src/fetch_coach_history.py` now hits `.de`. Bot-detection on scraping
targets is evidently something that changes under you, not a one-time
solve — worth remembering if this breaks again later. A resilience guard
was added at the same time: `fetch_coach_history()` now refuses to
overwrite an existing, larger `coach_history.csv` with a much smaller
result (see its docstring), because this exact failure silently wrote a
1-row file over ~1600 real rows the first time it happened, which broke
coach assignment for 98% of matches without a single crash anywhere in the
chain — a warning log, not an error, all the way down to
`coach_impact.py` quietly finding zero valid coaching changes.

## Setup

Requires **Python 3.10+** (`soccerdata` doesn't support 3.9). On this
machine that means using `/opt/homebrew/bin/python3.13` rather than the
system `python3`.

```bash
cd bundesliga-coach-impact
/opt/homebrew/bin/python3.13 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

On macOS, XGBoost also needs the OpenMP runtime, which isn't installed by
default (not on a fresh dev machine, and not on GitHub's `macos-latest`
Actions runners either — `.github/workflows/ci.yml`'s lockfile job hits
the exact same thing):

```bash
brew install libomp
```

Skipping this produces `XGBoostError: Library not loaded: @rpath/libomp.dylib`
the first time anything imports `xgboost`, not at install time — easy to
miss until you actually run something.

Prefer an exact-reproducible install instead? Use
`pip install -r requirements-lock.txt` (a `pip freeze` from a known-working
environment) in place of the `requirements.txt` line above — see that
file's header comment for when to regenerate it.

FBref access goes through a headless Chrome driver under the hood
(`soccerdata` uses `seleniumbase`) — the first run downloads a matching
`chromedriver` automatically.

## Run

```bash
python run_pipeline.py
```

This runs, in order: FBref fetch → Understat fetch → coach-history fetch →
merge → coach-impact analysis → formation-matrix analysis. Outputs land in
`outputs/`:

- `coach_impact_rankings.csv`
- `formation_matchup_matrix.csv` + `formation_matchup_heatmap.png`
- `coach_preferred_formations.csv`

Already have raw data cached and just want to re-run the analysis (e.g.
after editing `config.IMPACT_WINDOW`)?

```bash
python run_pipeline.py --skip-fetch
```

Or run one stage at a time while iterating:

```bash
python -m src.fetch_fbref
python -m src.fetch_understat
python -m src.fetch_coach_history
python -m src.build_dataset
python -m src.coach_impact
python -m src.formation_matrix
```

Once `match_dataset.parquet` exists, the outcome predictor and `predict.py`
(below) build on top of it.

## Formation-aware outcome predictor

`src/features.py` builds a leak-safe feature table: every rolling/cumulative
stat (form PPG, goal difference, xG difference, PPDA, deep completions,
season-to-date PPG, days into the current coach's tenure) is `.shift(1)`'d
before any window is applied, so a match's features only ever come from
that team's *strictly prior* matches. `src/outcome_predictor.py` trains a
Random Forest and an XGBoost classifier on that table to predict
win/draw/loss, with the two formations (own + opponent's) as categorical
features alongside the form stats.

```bash
python run_outcome_predictor.py
```

**Evaluation is a time-based holdout** — `config.TEST_SEASONS`
(2025-26 + the ongoing 2026-27) is held out entirely; training only ever
sees earlier matches. A random row-level split would leak future results
into training through the rolling features' shared history and wildly
overstate accuracy, which is a classic way sports-prediction demos quietly
cheat — this pipeline deliberately doesn't.

Latest run (616 held-out matches):

| | Accuracy | Macro F1 | vs. majority-class baseline (37.8%) | vs. home-advantage-only baseline (43.8%) |
|---|---|---|---|---|
| Random Forest (balanced) | 50.2% | 0.486 | +12.4pp | +6.4pp |
| **XGBoost (balanced)** | **50.5%** | **0.496** | **+12.7pp** | **+6.7pp** |

Both models clear the home-advantage baseline — the simplest signal a
football outcome model needs to beat to be worth anything — with the draw
class weighted to actually attempt predicting draws (unweighted, both
models learned it's "cheapest" to never predict D at all; recall on draws
alone jumped from 0% to 34-45% once weighted, at a small cost to overall
accuracy). Football match prediction genuinely tops out in this range in
published research — a much higher number here would be a leakage red flag,
not a win.

*(These numbers include `form_deep_completions`/`opp_form_deep_completions`
— Understat's raw response already carried deep completions through, just
unused; wiring it into `build_dataset.py`/`features.py`/`outcome_predictor.py`
moved both models up a couple points of macro F1 over the previous,
deep-completions-less run: 0.464→0.486 for Random Forest, 0.489→0.496 for
XGBoost — a genuine, if modest, improvement from a feature that was already
sitting in the raw data unused.)*

![XGBoost feature importance — form and season PPG dominate, but formation categories place throughout the top 15](docs/outcome_feature_importance.png)

Formation categories place throughout the top-15 feature importances (own
and opponent formation each contribute meaningfully, alongside home/away,
season form, xG form, and coach tenure) — real but secondary signal, not the
dominant one. `outputs/formation_matchup_predicted.png` shows the same
(formation, opponent formation) heatmap as the raw one above, but built from
the model's predicted win probability instead of the raw average — i.e.
adjusted for form and home advantage rather than conflating "this formation
wins more" with "teams using this formation also tend to be in better form":

![Form-adjusted formation matchup heatmap](docs/formation_matchup_predicted.png)

**Framing, honestly**: `formation`/`opp_formation` here are the formations
*actually fielded in that match* — known at kickoff to the two coaches, not
to a forecaster the day before. That makes this an explanatory model
("which formation choices tend to pair with wins, controlling for form") 
rather than a pre-kickoff bookmaker-style predictor.

### Pre-match forecaster variant

```bash
python run_prematch_predictor.py
```

Trains the genuine pre-match version: `formation`/`opp_formation` swapped
for `recent_formation`/`opp_recent_formation` — each team's most common
formation over its last `FEATURE_ROLLING_WINDOW` matches, computed the same
shift-safe way as every other feature (see `src/features.py`'s
`_rolling_mode`). Recent-formation matches the actual matchday formation
only about half the time, so this is a genuinely different, noisier
categorical signal — not a formality.

The result isn't the clean "pre-match is a bit worse, as expected" story
you'd guess going in:

| | Actual formation | Recent-formation (pre-match) | Δ macro F1 |
|---|---|---|---|
| Random Forest | 0.486 | **0.506** | **+0.020** |
| XGBoost | 0.496 | **0.507** | **+0.011** |

Both models now do slightly *better* on recent-formation than on the
actual matchday formation. That's a different result than before
`form_deep_completions` was added as a feature (see the main results table
above): back then Random Forest improved on recent-formation but XGBoost
got *worse* — an asymmetric pattern explained by `formation`'s 19 sparse
categories being noisier for Random Forest's default splits than
`recent_formation`'s 16, more-concentrated ones, while XGBoost's
regularization handled that noise well enough that the exact matchday
formation still won out. Adding a second strong numeric signal
(`form_deep_completions`) appears to have narrowed that gap for XGBoost too
— plausible, since it gives both models another good split to lean on
instead of needing formation's fine-grained categories as much — but these
deltas are small (0.011–0.020 macro F1 on a 616-match holdout, one run, no
repeated-seed averaging), so treat "XGBoost now prefers recent-formation
too" as directionally interesting, not as a confident reversal of the
earlier finding. You can still see the earlier asymmetry's fingerprint in
the feature importances — recent Random Forest leans almost entirely on
numeric form features with `recent_formation` barely registering, while
XGBoost still finds several `recent_formation` categories worth real
weight:

![Pre-match variant feature importance — Random Forest leans on numeric form features, XGBoost still weights several recent_formation categories](docs/outcome_feature_importance_prematch.png)

**Bottom line**: if you actually need a pre-kickoff forecast (the entire
point of "pre-match"), a model trained on actual-formation isn't usable —
you don't have that data before kickoff. Between the two untuned
pre-match-legal options here, XGBoost (0.507) and Random Forest (0.506)
are close enough to call a tie; [Hyperparameter tuning](#hyperparameter-tuning)
below is where a clear winner actually emerges (Optuna-tuned Random
Forest, 0.522) — see that section for the full comparison across tuning
methods, not just untuned numbers.

### Hyperparameter tuning

```bash
python run_tune_hyperparameters.py   # actual-formation variant
python run_tune_prematch.py          # pre-match (recent-formation) variant
python run_tune_optuna.py            # actual-formation, wider Optuna search
python run_tune_optuna_prematch.py   # pre-match, wider Optuna search
python run_tune_embargoed.py         # both variants, embargoed TimeSeriesSplit (see below)
```

All five (plus the two training scripts above and the native-categorical
one below) append to the same `outputs/outcome_model_metrics.json` rather
than overwriting each other, so results from every run you've done stay
visible side by side.

`src/tune_hyperparameters.py` grid-searches both models (`GridSearchCV`,
scoring on macro-F1) with **`TimeSeriesSplit`, not the default random
K-fold, for cross-validation** — a random K-fold would train on some
matches from *after* the ones it validates against within the same fold,
reintroducing the exact leakage the outer train/test split already guards
against, just one level down. Grid: `n_estimators`/`max_depth`/
`min_samples_leaf` for the forest, plus `learning_rate`/`subsample` for
XGBoost (12 and 16 combinations respectively). `config.N_CV_SPLITS`
controls the fold count (currently 10 — see below for why that number and
not something else).

**First pass, 5 folds**: tuning made every single model worse — 4 for 4 —
despite finding better configurations by CV score during the search every
time. The CV scores (0.41-0.44) sat well below the eventual test scores
(0.46-0.49), pointing at `TimeSeriesSplit`'s early folds (very little
training data) being a noisier optimization target than the final
602-match holdout.

**Fixing that meant actually checking what raising `n_splits` does, not
assuming "more folds" helps by default.** sklearn's `TimeSeriesSplit(n_splits=N)`
divides the training set into `N+1` equal chunks — raising `N` shrinks
*every* chunk, including the earliest, already-data-starved one:

```
n_splits=5:  fold 0 train=568  fold 4 train=2824  (test=564 every fold)
n_splits=10: fold 0 train=308  fold 9 train=3080  (test=308 every fold)
```

So doubling the fold count could easily have made the noisy-early-fold
problem worse, not better — it was an empirical question, not a safe
assumption, which is why it got tested rather than just bumped. Verified
live before committing to a full run.

**Result at 10 folds — genuinely different, and more interesting than
either "tuning never helps" or "more folds fixes everything":**

| | Untuned | GridSearchCV (10-fold) | Optuna, 50 trials (10-fold) |
|---|---|---|---|
| Random Forest, actual | 0.486 | **0.489** | 0.492 |
| XGBoost, actual | **0.496** | 0.477 | 0.449 |
| Random Forest, pre-match | 0.506 | 0.498 | **0.522** |
| XGBoost, pre-match | **0.507** | 0.471 | 0.470 |

*(macro F1 on the real held-out test set; bold = best per row)*

More folds **genuinely helped Random Forest on actual-formation** (+0.003
over untuned) and **Optuna helped it more** (+0.006), continuing the
reversal from the 5-fold result where tuning made everything worse.
**XGBoost still doesn't beat untuned in either variant with GridSearchCV or
Optuna** — model-dependent, not a uniform fix, tracking the earlier
formation-variant finding that Random Forest and XGBoost don't respond to
changes the same way on this dataset. The standout result is
**Optuna-tuned Random Forest on pre-match (0.522)** — clearly the best
pre-match-legal number found anywhere in this project, and the reason
`predict.py`'s pre-match default is Optuna, not GridSearchCV.

**Optuna's wider search still doesn't reliably beat GridSearchCV** —
worse on actual-formation XGBoost (0.449 vs 0.477, the same overfitting-
the-CV-signal pattern documented in the original 5-fold-vs-10-fold
investigation: a wider search finds a sharper fit to noisy CV scores, not
a genuinely better model) and on pre-match XGBoost (0.470 vs 0.471, a
toss-up), but clearly ahead on both Random Forest rows. Not "Optuna is
better" or "Optuna overfits" as a blanket rule — which model, and which
formation variant, still matters more than which search method.

**Does an embargo fix XGBoost's gap specifically?** (`run_tune_embargoed.py`,
`config.CV_EMBARGO_GAP`) — the untried lever flagged after the 5-fold→10-fold
investigation: XGBoost never beat its untuned baseline under GridSearchCV
or Optuna, in either variant, so an 18-row (one matchday) embargo between
each `TimeSeriesSplit` fold's train and validation slice was tried next
(see `src/tune_hyperparameters.py`'s `gap` parameter docstring for the full
reasoning — briefly: a validation fold's earliest rows are otherwise
immediately time-adjacent to training rows, so their rolling-form features
are highly serially correlated with what the model just trained on,
inflating validation scores in a way that doesn't generalize):

| | Tuned (no embargo) | Tuned + 18-row embargo | Δ |
|---|---|---|---|
| Random Forest, actual | **0.489** | 0.475 | −0.014 |
| XGBoost, actual | 0.477 | **0.491** | **+0.014** |
| Random Forest, pre-match | **0.498** | 0.497 | −0.001 |
| XGBoost, pre-match | 0.471 | **0.506** | **+0.035** |

**This is the cleanest confirmation yet that the CV-vs-test gap was
specifically an XGBoost problem, not a Random Forest one**: the embargo
helped XGBoost in both variants (+0.014, +0.035) — on pre-match it's now
essentially tied with untuned (0.506 vs 0.507) instead of clearly behind
(0.471) — while it made Random Forest slightly *worse* in both variants.
The embargo didn't necessarily make the CV score itself a more accurate
predictor of test performance (actual-formation XGBoost's CV score barely
moved, 0.407→0.409) — what changed is which hyperparameters GridSearchCV
selected: on pre-match, embargoed search picked `max_depth=5, subsample=1.0`
where the no-embargo search had picked `max_depth=3, subsample=0.8`, a
concretely different, less conservative model that happened to generalize
much better. Random Forest, whose problem was never the CV-vs-test gap in
the first place (it already beat untuned without any embargo), had nothing
to fix here and the extra embargo just cost it some usable training data
per fold.

**Bottom line**: no single tuning method — GridSearchCV, Optuna, or the
embargoed variant — is uniformly best; which one to use depends on the
model AND the formation variant. Across every method tried, the two
strongest options are **XGBoost on actual formation (untuned, 0.496)** for
the explanatory model, and **Optuna-tuned Random Forest on pre-match
(0.522)** for the genuine pre-match forecaster — both are what
`predict.py` defaults to. The embargoed variant is the best *specifically
for pre-match XGBoost* (0.506, nearly matching untuned) if you want a
tuned-with-documented-hyperparameters model there instead of the untuned
one. All sixteen model files (untuned/`_tuned`/`_tuned_embargoed`/`_optuna`
× 2 formations × 2 model types) save separately under `outputs/models/`
rather than overwriting each other.

### XGBoost native categorical support

```bash
python run_xgboost_native_categorical.py
```

One more lever, tried and documented rather than left as a guess: XGBoost
2.0+ can split directly on categorical values (`enable_categorical=True` +
pandas `category` dtype) instead of one-hot encoding them. The theory —
one-hot encoding ~19 formation categories creates a lot of sparse binary
columns a boosted tree has to reconstruct a categorical split from across
several splits, where native support partitions the categories in one —
was plausible enough to actually test, holding every hyperparameter
identical to the untuned one-hot baseline so the encoding is the only
thing that changes:

| | One-hot (baseline) | Native categorical |
|---|---|---|
| XGBoost, actual | **0.496** | 0.466 |
| XGBoost, pre-match | **0.507** | 0.501 |

*(macro F1 on the real held-out test set)*

**One-hot wins both.** Clearly on actual-formation (−0.030); much closer
on pre-match (−0.006, within the range that could plausibly be noise on a
single 616-match holdout). The plausible explanation is the mirror image
of the theory that motivated trying this: at `max_depth=4` (the baseline's
depth, held fixed for a fair comparison), one-hot gives each formation its
own independent split threshold in a single level of the tree, while a
native categorical split has to partition all ~19 categories into two
groups per split — reaching one-hot's effective resolution needs more
depth than this comparison allowed. Native categorical support is
generally pitched at *much* higher cardinality (hundreds/thousands of
categories, where one-hot's column explosion is the real problem) — 19 is
apparently not where it pays off, at least not at this tree depth. Not
wired into `predict.py`, since it's a loss (clear on one variant, likely
on the other) rather than a close call worth keeping both options for.

## Coach bounce predictor

```bash
python run_coach_bounce.py
```

A different question from the outcome predictor above: for a coaching
CHANGE, can the SIZE of the resulting PPG swing (`coach_impact.py`'s
`ppg_delta`) be predicted from the team's pre-change form plus the
INCOMING coach's own historical track record — how they performed, on
average, in whatever earlier matches *they* coached (at any club) that are
already in this dataset? `src/coach_bounce.py` builds this as a coach-level
join, not a team-level one: for every row in `coach_impact_rankings.csv`,
every `match_dataset.parquet` row where `coach == incoming_coach` and
`date < change_date` (regardless of which club that was at) becomes that
coach's track record going into this appointment — the leak-safety
property here, same spirit as `features.py`'s `.shift(1)`.

**The honest headline finding, up front**: only 32 of the 107 coaching
changes in the dataset have *any* prior match history for the incoming
coach at all — most incoming coaches are either new to management within
this window, or their previous job predates `config.SEASONS`, or was
outside the Bundesliga entirely, none of which this dataset can see.
Requiring a usable sample size (`MIN_PRIOR_MATCHES = 10`) leaves **28
rows**. That's nowhere near enough to trust a model trained on it, whatever
the reported R² says — so it's reported here with leave-one-out
cross-validation (the only honest option at this n; a fixed train/test
split would put ~6 rows in the test fold) against a trivial "always predict
the training-fold mean" baseline, not as a claim this is a usable
predictor:

| | Leave-one-out R² | Leave-one-out MAE |
|---|---|---|
| RidgeCV (this model) | −0.044 | 0.523 |
| Baseline (predict the mean) | −0.075 | 0.578 |

![Coach-bounce predictor: leave-one-out predicted vs. actual PPG delta, n=28](docs/coach_bounce_predicted_vs_actual.png)

Both R² values are negative — neither the model nor the trivial baseline
beats "no information" by much on this sample, and the model's edge over
the baseline (MAE 0.523 vs 0.578, about a 10% reduction) is small and, at
n=28, not something to read much into. **This is a negative-to-marginal
result, reported with the same rigor as the positive ones elsewhere in
this README** (see [XGBoost native categorical support](#xgboost-native-categorical-support)
for another) — not because 28 coaching changes is a rigorous test of the
hypothesis, but because 28 is genuinely all there currently is, and
pretending otherwise would be the more dishonest choice.

One piece of the fitted `RidgeCV` model's coefficients is worth calling
out even given the sample-size caveat, because it's the intuitive result,
not a surprising one: `ppg_before` has by far the largest-magnitude
coefficient (−0.73, next-largest is 0.36) — a team doing *worse* before
the change is associated with a *bigger* positive swing after it, i.e.
mean reversion. That's exactly what you'd expect (a struggling team has
more room to improve than one already doing well) and is reassuring as a
sanity check on the pipeline, even though it isn't the interesting new
signal this model was actually built to test for (the incoming coach's own
history) — `coach_hist_ppg`'s coefficient (+0.22) is positive but much
smaller, consistent with "some" signal, not "enough to matter yet."

## Predicting a match

Everything above trains and evaluates models; `predict.py` is the piece
that actually uses one:

```bash
python predict.py --list-teams
python predict.py --team "Bayern Munich" --opponent Dortmund --venue home
```

```
Bayern Munich (home=True) vs Dortmund
Model: random_forest (prematch, optuna-tuned)

  Bayern Munich win 36.7%  ###############
  Draw             39.1%  ################
  Dortmund win     24.2%  ##########

Bayern Munich form: PPG(last 5)=2.20  season PPG=2.00  coach=Vincent Kompany (806d)  recent formation=4-2-3-1  (as of 2026-09-05)
Dortmund form: PPG(last 5)=3.00  season PPG=3.00  coach=Niko Kovac (590d)  recent formation=3-4-3  (as of 2026-09-12)
```

It computes each team's *current* form directly from
`data/processed/match_dataset.parquet` and `coach_history.csv` — the same
feature definitions `src/features.py` uses for training, just evaluated as
of right now instead of shifted away from a specific past match (there's
no "next match" row in historical data to attach features to; the rolling
window is simply the team's actual most recent matches — see
`current_team_state()`'s docstring and `tests/test_predict.py` for the
exact semantics, including a real off-by-one bug that coverage caught: an
earlier version of `recent_formation` here reused `features._rolling_mode`
directly, which is correct for a *past* match but excludes the team's most
recent PLAYED match, making it one match stale for "right now" — fixed and
regression-tested). Defaults to the strongest pre-match-legal model
(Optuna-tuned Random Forest on recent-formation — see
[Hyperparameter tuning](#hyperparameter-tuning)).

Pass both `--formation` and `--opp-formation` to switch to explanatory
mode instead (defaults to untuned XGBoost) — answers "what does the model
think GIVEN these formations," not a genuine forecast, since you don't
know the opponent's actual matchday formation in advance:

```bash
python predict.py --team "Bayern Munich" --opponent Dortmund --venue home \
    --formation 4-2-3-1 --opp-formation 4-3-3
```

`--model {random_forest,xgboost}` and `--tuning {none,grid,optuna}`
override which of the sixteen saved model files gets used, if you want to
compare them directly on the same matchup (`--tuning grid` also picks up
the embargoed variant automatically where it exists — see
[Hyperparameter tuning](#hyperparameter-tuning)). Typos in `--team`/`--opponent`
get a "did you mean" suggestion rather than a bare KeyError.

## Automated weekly refresh

`scripts/weekly_refresh.sh` reruns `run_pipeline.py` (FBref/Understat/
Transfermarkt fetch → merge → coach-impact and formation analysis) and
logs the result to `logs/refresh_<timestamp>.log` (last ~12 kept). It's
scheduled via **`launchd`, not `cron`** — deliberately: `cron` simply skips
a job entirely if the Mac is asleep or off at the scheduled time, while
`launchd`'s `StartCalendarInterval` evaluates missed schedules on wake and
login and runs them then instead. Not a hard real-time guarantee (it's "as
soon as launchd notices," not instantaneous), but a real, documented
difference from `cron` that matters a lot for a laptop that sleeps.

Install (every Monday 06:00, catching the weekend's matches; edit the
`Weekday`/`Hour`/`Minute` in the plist first if you want a different time):

```bash
cp scripts/com.felixnitschke.bundesliga-coach-impact.weeklyrefresh.plist \
   ~/Library/LaunchAgents/
launchctl bootstrap gui/$(id -u) \
   ~/Library/LaunchAgents/com.felixnitschke.bundesliga-coach-impact.weeklyrefresh.plist
```

Check it's loaded and see when it last ran:

```bash
launchctl print gui/$(id -u)/com.felixnitschke.bundesliga-coach-impact.weeklyrefresh
```

Uninstall:

```bash
launchctl bootout gui/$(id -u)/com.felixnitschke.bundesliga-coach-impact.weeklyrefresh
rm ~/Library/LaunchAgents/com.felixnitschke.bundesliga-coach-impact.weeklyrefresh.plist
```

**Known limitations, honestly:**
- Only catches up on a *missed schedule*, not a fully powered-off Mac that
  stays off past when it would next check — it still needs to actually
  boot and have you logged in at some point for the catch-up to fire.
- Nothing notifies you of a failure. `logs/launchd_stderr.log` and the
  latest `logs/refresh_*.log` (which explicitly logs `FAILED (exit N)`
  rather than a misleading "finished OK" if `run_pipeline.py` errors) are
  the only records — check them occasionally, or wire up a real
  notification (e.g. `osascript -e 'display notification ...'` on failure,
  or an email) if silent failures are a real concern for how you're using
  this.
- All three raw fetches — Transfermarkt, FBref, Understat — now share the
  same "refuse to shrink drastically" guard (`src/data_guard.py`), so an
  unattended weekly run that hits a blocked/broken source fails loudly
  (a `RuntimeError`, visible in `logs/refresh_*.log` as `FAILED`) rather
  than silently writing a degraded dataset. FBref also has a second,
  more targeted guard specific to it: it checks the *number of teams*
  that fetched successfully, not just row count, since FBref lists a
  whole season's fixtures whether played or not — a row-count check
  alone wouldn't reliably catch some teams failing.
- What's still unguarded: `build_dataset.py`'s merge step and everything
  downstream of it (the outcome-predictor feature table, trained models).
  A garbled-but-not-drastically-smaller upstream fetch (e.g. a source
  corrupting values without changing row counts) would still flow through
  silently. The three raw fetches are the actual entry points for bad
  external data, so guarding there covers the most likely failure modes,
  but it isn't an exhaustive guarantee.

## Testing

```bash
python -m pytest tests/
```

Covers the properties this project actually depends on being correct,
none of which a wrong answer would necessarily *look* wrong:

- **Leak-safety** (`tests/test_features.py`) — every rolling/cumulative
  feature must depend only on strictly-prior matches. Verified by hand-
  computing expected values on small synthetic teams and asserting exact
  agreement, plus one test that deliberately checks two teams' histories
  don't blend together. To confirm these tests actually have teeth (not
  just checking their own assumptions), a `.shift(1)` was temporarily
  removed from the source during development and confirmed the affected
  test failed loudly — then restored.
- **Time-based splitting** (`tests/test_outcome_predictor.py`) — the
  train/test split must never let a test-set row's date precede a
  training-set row's date, and must raise loudly rather than silently
  evaluate on an empty set if `config.TEST_SEASONS` ever drifts out of
  sync with the data (exactly what happened once during development).
- **The overwrite guards** (`tests/test_data_guard.py`,
  `tests/test_fetch_coach_history.py`) — a direct regression test for the
  Transfermarkt-blocking incident described under
  [Data sources](#data-sources): simulates every club's fetch failing and
  asserts the existing good file survives untouched rather than being
  silently replaced by a near-empty one.
- **The Transfermarkt-id/team-name auto-resolution**
  (`tests/test_fetch_coach_history.py`, `tests/test_team_name_matcher.py`)
  — validates every id/name pair already known correct still resolves
  (12/12 ids, 28/28 names), plus the search/verify/cache/reject flow itself
  via mocks (a rejected guess must never get cached).
- **The coach-bounce predictor's coach-level join**
  (`tests/test_coach_bounce.py`) — same leak-safety property as the first
  bullet above, but for a join keyed on coach identity across clubs rather
  than a per-team rolling window: an incoming coach's historical profile
  must include only their OWN matches strictly before the change being
  predicted, at any club, and a coaching change with too thin a track
  record must be dropped rather than kept with a noisy 1-2-match average.
- **`predict.py`'s live feature computation** (`tests/test_predict.py`) —
  `current_team_state()` wasn't unit-tested at all until this pass; now
  covered against hand-computed values, including a real regression test
  for the `recent_formation` staleness bug this coverage found and fixed
  (see [Predicting a match](#predicting-a-match)).

All tests use small synthetic data, not the live scraped dataset — no
network access needed to run them, and they don't depend on however much
data happens to be sitting in `data/` on a given machine. CI
(`.github/workflows/ci.yml`) runs this plus `ruff` lint on every push/PR,
matrixed across Python 3.11 and 3.13, plus a separate job verifying
`requirements-lock.txt` installs cleanly.

A second, separate workflow (`.github/workflows/e2e-fixture.yml`, weekly +
manual `workflow_dispatch`, deliberately not on every push) runs
`scripts/e2e_fixture_pipeline.py`: a small, checked-in-as-code fixture
dataset (two fake teams, real schema copied from the actual
`data/raw/*.parquet` files) run through the REAL `build_dataset.py` →
`coach_impact.py` → `formation_matrix.py` → `features.py` →
`outcome_predictor.py` chain — everything the unit tests above exercise in
isolated pieces, but never wired together end to end, and never against
the actual rename/merge/join code paths real scraped data goes through.
Closes a real gap: a schema mismatch between what `fetch_fbref.py`/
`fetch_understat.py` save and what `build_dataset.py` expects (e.g. from a
future `soccerdata` release) would sail through every unit test above and
only surface the next time someone actually runs the real pipeline.

## Configuration

Everything tunable lives in `config.py`:

- `SEASONS` — how far back to pull. Formation and PPDA coverage is reliable
  from ~2014-15 onward; the default runs 2019-20 through the ongoing
  2026-27 season. Unplayed fixtures in an in-progress season are dropped
  automatically in `build_dataset.py` (they'd otherwise pad out
  matches-played counts with rows that have no actual result).
- `FEATURE_ROLLING_WINDOW` / `TEST_SEASONS` / `MODEL_DIR` — outcome
  predictor settings: rolling-form window size, which seasons are held out
  for evaluation, where trained models get saved.
- `CLUB_TRANSFERMARKT_ID` — team name → Transfermarkt numeric club id, used
  to build that club's manager-history URL. A newly promoted club not yet
  in this dict gets looked up automatically instead (see "Auto-resolution"
  under [Known rough edges](#known-rough-edges-this-is-a-scaffold-not-a-finished-pipeline))
  — this dict is now the hand-verified, permanent overrides, not the only
  source.
- `TEAM_NAME_MAP` — Understat's team names don't match FBref's; this maps
  Understat's spelling to the canonical FBref one used everywhere else.
  Same auto-resolution story as `CLUB_TRANSFERMARKT_ID` above (fuzzy match
  instead of a search, see `src/team_name_matcher.py`) for anything not
  already in this dict.
- `IMPACT_WINDOW` — how many matches before/after a coaching change count as
  the "before" and "after" samples (default 8).
- `N_CV_SPLITS` — `TimeSeriesSplit` fold count for hyperparameter tuning
  (see [Hyperparameter tuning](#hyperparameter-tuning) for why this is 10
  and not the sklearn default).
- `CV_EMBARGO_GAP` — rows excluded between each `TimeSeriesSplit` fold's
  train and validation slice for `run_tune_embargoed.py` (see
  [Hyperparameter tuning](#hyperparameter-tuning) for why 18, not an
  arbitrary round number).

## Known rough edges (this is a scaffold, not a finished pipeline)

- **Column names**: the exact columns `soccerdata` returns can shift
  slightly between versions. Every fetch script logs the columns it got on
  first run — if `build_dataset.py` or `formation_matrix.py` throws a
  `KeyError`/`RuntimeError`, check that log line first before assuming the
  scraper logic is wrong.
- **Transfermarkt club ids**: most of `CLUB_TRANSFERMARKT_ID` were verified
  live at some point (either by hand when first added, or automatically —
  see auto-resolution below, which strictly verifies every id it guesses),
  but not every single one has been individually re-checked recently. The
  scraper compares the fetched page's `<title>` against the club name and
  logs a loud warning (or, for an auto-resolved id, rejects it outright) if
  something looks wrong, so a bad id shouldn't fail silently — but do
  spot-check `data/processed/coach_history.csv` against the live
  Transfermarkt page for a club or two before trusting the impact rankings.
  Very short caretaker spells (a handful of matches) are the most likely
  thing to produce a noisy-looking row — `matches_before`/`matches_after`
  in the output tell you when a row is thin.
- **FBref rate limiting**: `soccerdata` paces requests to be polite, so a
  fresh 6-season pull takes a few minutes, not seconds. Cached responses
  live under `data/raw/` (soccerdata also has its own cache dir under
  `~/soccerdata/data/`) so re-running doesn't re-fetch everything.
- **Small-sample cells**: the formation heatmap hides any (formation,
  opponent formation) pairing with fewer than `MIN_MATCHUP_SAMPLES` (5)
  matches — a single upset shouldn't paint a whole cell green or red.
- **New teams used to need a hand-added `CLUB_TRANSFERMARKT_ID`/
  `TEAM_NAME_MAP` entry every time `SEASONS` widened or a promotion
  happened — this happened three times before it got automated.** Now a
  team missing from both gets resolved live instead: `src/transfermarkt_search.py`
  searches Transfermarkt for a club id (verified strictly against the
  page's `<title>` — a mismatch rejects the guess rather than trusting it,
  since nobody's manually double-checked an auto-resolved id the way a
  `config.CLUB_TRANSFERMARKT_ID` entry has been) and
  `src/team_name_matcher.py` fuzzy-matches an Understat name against
  FBref's team list (validated against all 28 pairs already known correct,
  including "FC Cologne" → "Köln" — an English/German name translation
  with no shared substring, which still resolves at a clear margin from
  the next-best guess). Both cache successful resolutions to
  `data/club_transfermarkt_ids_auto.json` / `data/team_name_map_auto.json`
  so it's a one-time cost per club, not a recurring one. A search or match
  that isn't confident still falls back to the same manual-entry path as
  before — this narrows how often that's needed, it doesn't claim to
  eliminate it.
- **A `pd.Timestamp.today()` bug already bit this once**: an early version
  of `fetch_coach_history.py` mapped an incumbent coach's blank "still
  active" end-date to *today's date* instead of leaving it open-ended. That
  silently capped every current coach's tenure at scrape time, so every
  future/in-progress-season fixture got no coach assigned at all once
  `SEASONS` grew to include the ongoing season. Fixed by leaving it as
  `None`/NaT and letting `build_dataset.py`'s `fillna(2100-01-01)` treat it
  as open-ended — worth knowing about if you ever touch date parsing here.
- **pandas 3.0 + pyarrow-backed columns**: comparing a pyarrow-backed
  Series's raw `.values` against a plain numpy array (e.g. in a baseline
  accuracy calculation) raises `AttributeError: 'ArrowExtensionArray'
  object has no attribute 'mean'` instead of just working. Use `.to_numpy()`
  rather than `.values` when you need a real numpy array out of a column
  read from these parquet files.
- **`predict.py`'s `recent_formation` was one match stale, silently, until
  a test caught it**: `current_team_state()` used to compute it by calling
  `features._rolling_mode(...)` and taking the last element — correct for
  a row attached to a *past* match (where excluding that match's own
  formation is exactly the point), but wrong for "the team's tendency
  right now," which should include the most recently PLAYED match, the
  same way the numeric form stats already do via `.tail(window)`. Verified
  live before fixing: 5 of 28 teams' reported `recent_formation` disagreed
  between the old and corrected computation, including a team that had
  just switched formation in its most recent match. Fixed in
  `_recent_formation()`; `tests/test_predict.py` has the regression test.
  A reminder that "the same feature definitions as training, just
  evaluated as of now" is easy to state and easy to get subtly wrong in
  the details — worth writing the test even when a function looks like a
  wrapper around already-tested code.

## Extending

- Swap `config.LEAGUE`/`SEASONS` to `"GER-Bundesliga2"` (verify the exact
  code via `soccerdata.FBref(leagues=...).available_leagues()`) to run the
  same pipeline on 2. Bundesliga.
- The embargoed `TimeSeriesSplit` (see [Hyperparameter tuning](#hyperparameter-tuning))
  was only tried with `GridSearchCV`, not `run_tune_optuna.py`'s own
  `TimeSeriesSplit(n_splits=N_CV_SPLITS)` (no `gap=`) — worth checking
  whether it also curbs Optuna's overfitting-the-CV-signal problem for
  XGBoost, or whether TPE's wider search just finds a different way to
  overfit the now-embargoed signal instead. Also only one gap size (18
  rows, one matchday) was tried — a small sweep (e.g. half/double that)
  would show whether the specific value matters or any meaningful embargo
  helps similarly.
- Optuna got *more* prone to overfitting the CV signal at 10 folds, not
  less — worth understanding whether a narrower, more targeted search
  space (informed by which hyperparameters the GridSearchCV winners share)
  does better than TPE's free rein over 9 dimensions at once.
- Try target = expected points / goal difference (regression) instead of
  win/draw/loss (classification) — draws are inherently the hardest class
  here, and a lot of that difficulty may just wash out with a continuous
  target.
- XGBoost's native categorical split support lost to one-hot on both
  variants (see [XGBoost native categorical support](#xgboost-native-categorical-support))
  — worth retrying at a greater max_depth specifically for the categorical
  variant, since the working theory for why it lost is that it needs more
  depth to reach one-hot's effective resolution, not that categorical
  splits are inherently worse here.
- The Transfermarkt-id/team-name auto-resolution only fills in GAPS -- it
  never re-checks an existing `config.CLUB_TRANSFERMARKT_ID`/
  `TEAM_NAME_MAP` entry, so a manually-configured id that quietly went
  stale (Transfermarkt restructuring a club's page, say) wouldn't get
  caught automatically. Periodically re-running the search for already-
  configured clubs and diffing against the hardcoded values would catch
  that class of drift, at the cost of extra requests on every run.
- The [coach bounce predictor](#coach-bounce-predictor)'s usable sample is
  only 28 coaching changes (of 107 total) — it will grow every time
  `SEASONS` widens (more history for an incoming coach to have a track
  record in) and every season that passes. Worth re-running periodically
  to see whether the leave-one-out R² turns positive with a larger n,
  rather than treating today's negative result as final. A coach's more
  recent matches probably matter more than their career average too — a
  recency-weighted profile (e.g. last-N-matches mean rather than
  all-time mean) is an easy, untried variant once there's enough data per
  coach to make windowing meaningful.
- `scripts/e2e_fixture_pipeline.py` exercises `build_dataset.py` →
  `coach_impact.py` → `formation_matrix.py` → `features.py` →
  `outcome_predictor.py`, but not the tuning scripts, the native-categorical
  experiment, or `coach_bounce.py` — those either need a larger fixture
  (the coach-bounce join needs a coach with real prior-club history, which
  the current 2-team fixture doesn't have) or are slow enough
  (`GridSearchCV`/Optuna) that adding them to a weekly job is a real cost/
  benefit tradeoff, not just an oversight.
- `predict.py`'s CLI layer itself (`main()`, argument parsing, the
  `--formation`/`--opp-formation` "give both or neither" validation) still
  isn't covered by a test — `tests/test_predict.py` covers
  `current_team_state()`, the feature-computation core, but not the
  argparse wiring around it. A subprocess- or `monkeypatch.setattr(sys,
  "argv", ...)`-based test invoking `main()` end to end would close that
  remaining layer.
